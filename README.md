# ci-guard — сторож ключей для всех репозиториев организации

Один проход CI, объявленный через `workflow_call`. Вызывается из любого
репозитория восемью строками, логика живёт здесь.

## Подключить к репозиторию

1. Скопировать [primer/guard.yml](primer/guard.yml) в
   `.github/workflows/guard.yml` своего репозитория.
2. Завести в своём репозитории `.gitleaks.toml` — исключения у каждого
   проекта свои, поэтому файл живёт рядом с кодом, а не здесь.
3. По желанию скопировать [primer/settings.json](primer/settings.json) в
   `.claude/settings.json` — тогда открывший репозиторий получит общие
   своды правил из `x10company/claude-skills`.

## Сторож до коммита, а не после

Проход CI ловит уже уехавшее: секрет, попавший на сервер, придётся менять,
даже если проход покраснел. До отправки то же самое ловит хук — и берёт он
сторожа отсюда, по номеру версии, а не копией в своём репозитории.

Копий не держим по той же причине, по которой проход CI живёт здесь: копия
расходится при первой же правке правил, и заметить это нечем.

В проверяемом репозитории — файл `.pre-commit-config.yaml`:

```yaml
repos:
  - repo: https://github.com/x10company/ci-guard
    rev: v1.0.0
    hooks:
      - id: check-secrets
```

На машине — один раз, и один раз в каждом клоне:

```bash
brew install pre-commit          # на маке; иначе pip install pre-commit
pre-commit install               # в корне клона: ставит .git/hooks/pre-commit
pre-commit run check-secrets     # прогнать сторожа по тому, что в индексе
```

Сторож смотрит в индекс, а не в рабочее дерево: пустой индекс — это
«коммитить нечего», а не «чисто». Подкладывание пробы поэтому делается
через `git add`, а не правкой файла на диске.

Версия двигается явно, командой `pre-commit autoupdate`, — и это разница
между ссылкой и копией: обновление видно диффом одной строки, а не сверкой
двух файлов.

**Хук не принуждение.** Его обходят ключом `--no-verify`, и он молчит на том,
что уже лежит в истории. Последнее слово остаётся за проходом CI, а хук
экономит ротацию ключа, которую иначе пришлось бы делать.

## Что проверяет

| Шаг | Что делает |
|---|---|
| Самопроверка | подкладывает пробу под каждое правило и печатает, какие ещё видит |
| Сторож | ключи, токены, приватные ключи, случайные значения по энтропии, абсолютные пути |
| gitleaks | второе мнение по текущему состоянию файлов, без истории |
| Синтаксис JS | `node --check`, пропуская скрипты Airtable |

## Почему самопроверка идёт первой

Правило легко ослепить неудачной строкой в списке исключений. У нас
аллоулист `abcdefghijklm` однажды спрятал настоящий ключ Stripe, и это
нашлось подкладыванием, а не чтением правил. Пустой результат — это
«ничего не проверено», а не «всё хорошо».

## Видимость репозитория

Проход выкачивает этот репозиторий в вызывающий (`path: .ci-guard`). Штатный
`GITHUB_TOKEN` вызывающего репозитория читает только его самого, поэтому
**этот репозиторий должен быть публичным или internal**. Секретов в нём нет:
здесь только правила поиска, а исключения с внутренними путями остались в
проектах. Если оставлять приватным — придётся передавать отдельный токен
в шаге выкачки.
